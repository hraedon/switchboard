## NON-BLOCKING findings

**1. Load-path `peak_windows` validation silently swallows garbage — commit message overclaims.** `src/switchboard/config_store.py:745-755` + `:703-712`
`_peak_windows_list` catches `JSONDecodeError` and filters non-string entries, returning `[]`; `_validate_row` then validates `parse_peak_windows([])` which trivially passes. A row whose `peak_windows` cell holds malformed JSON (e.g. `"{oops"`), a non-list (`"{}"`), or a list of non-strings is **silently accepted on load as "no windows"** — the row loads, the provider builds, and the windows are gone. The commit message claims "validated on every write **AND on load (a bad row is refused with the spec named)**" and the design rationale is precisely "a window that silently didn't parse would mean burning quota at the expensive rate with no sign why" — which is exactly what this gap permits (peak protection silently lost → expensive burn). Reachable only by external DB tampering (all API write paths validate via `_normalize_peak_windows`), so it's a defense-in-depth hole, not a live path — but fix the asymmetry: have `_validate_row` strict-parse the raw string (propagate `JSONDecodeError`/shape errors) instead of funneling through the lenient decode.

**2. Partial PUT silently wipes `peak_windows`/`dashboard_provider` (whole-row upsert).** `src/switchboard/config_store.py:294-307` + `src/switchboard/admin.py:2587-2589`
`upsert` is whole-row: any PUT body omitting the new fields (a cached pre-025 GUI page mid-deploy, a scripted admin client, a future GUI change) resets them to NULL with no error — silently disabling peak demotion and the dashboard mapping. The current GUI always sends them (`dashboard.html:666,670`), so the browser path is safe; but unlike `api_key_stored` (kept-on-absent), the new fields have no merge protection. Consider extending the keep-on-absent semantics (or documenting loudly) given finding 1's failure mode compounds this one.

**3. Add-mode quick-add 400s; the "server default" comment is wrong.** `src/switchboard/static/dashboard.html:696-711` + `src/switchboard/config_store.py:361`
The comment "env with a blank var name omits key_mode so the server default applies (quick-add)" is factually wrong — `_build_row` calls `_req_str(fields, "key_mode")` and there is **no** server default; omitting `key_mode` raises `ValueError` → 400 "field 'key_mode' is required". In add mode the selector defaults to `env`, so a quick-add (name + upstream only, no env var typed) falls through all three branches, sends no `key_mode`, and 400s with a confusing message. Pre-025 behaved identically (not a regression), but Plan 025 §3d explicitly promises "Add stays a quick form: create, then Edit" — that promise isn't delivered for the credential-less case, and the new selector makes `env` look like a valid no-input choice. Fix: send `key_mode='passthrough'` when the env field is blank in add mode (or add the server-side default the comment assumes). The GUI harness doesn't cover this path (all add tests set a mode explicitly).

**4. stored→passthrough switch erases the stored key without the promised "warning inline".** `src/switchboard/static/dashboard.html:307-312`
Plan §3d: "switching to `passthrough` is a one-click downgrade with the warning inline". The delivered passthrough block describes passthrough semantics but never warns that an existing stored credential **will be permanently erased** from the store row (the server does erase it — whole-row upsert with `key_mode='passthrough'`, `api_key_stored=None`). A misclick costs the operator a re-entry of the full key. Add an explicit "this erases the stored key" warning when `existing.key_mode === 'stored'` and the selector moves to passthrough.

**5. `snapshot_provider_state` evaluates `in_peak` against the wall clock, ignoring its `now` argument.** `src/switchboard/providers.py:538-540`
The function accepts `now` (used for budget utilization) but computes `in_peak` from `_time.time()` — consistent with the pre-existing `quota_resets_in`/`weekly_reset_in` pattern, so it's a defensible "the shell owns the wall clock" choice, but it makes the field non-reproducible and forces tests to contrive always-on windows (`tests/test_providers.py:test_snapshot_in_peak_from_windows` acknowledges this). A one-line `now`-parameter pass-through would make the shell deterministic for free and let tests pin real boundary times.

**6. Peak badge renders only in-peak; plan promised off-peak badge too.** `src/switchboard/static/dashboard.html:1653`
Plan §3d: cards show "`peak (ends 2h 10m)` / `off-peak (peak in 3h)`". Delivered: the badge only appears when `in_peak` is true; off-peak state/countdown lives in the Peak Pricing section instead of a badge. Cosmetic deviation, but the plan's wording (and the commit's "peak badge" claim) overstates the card-level rendering.

**7. `next_boundary` edge cases (display-only, bounded).** `src/switchboard/peak.py:169-183`
The minute-scan terminates (8-day bound; a weekly pattern flips within 7 days), and worst case — always-on complementary windows like the test's `00:00-12:00`+`12:00-00:00` — costs ~11.5k `in_peak` evaluations per provider per status request (~tens of ms; status is rebuilt per request at `admin.py:450`). Acceptable for a 5s-poll display, but two nits: (a) a boundary landing exactly at the current minute is skipped (scan starts at the next whole minute), so the countdown can jump to the *next* boundary; (b) the constant-state case returns `None` after the full scan rather than early-exiting. Cosmetic.

## Notes on the numbered attack directions (all cleared unless listed above)

- **Peak parsing** (direction 1): boundaries, `fri 22:00-08:00` on Sat 03:00 (in) vs Sun 03:00 (out), `fri-mon` wrapping, `-07:00`, and end-exclusive-across-midnight all verified correct (`peak.py:107-137,146-158`); the regex is linear with no nested quantifiers — no ReDoS; day-set parsing is bounded; the `+15:00`/`25:00`/zero-length rejects are covered (`tests/test_peak.py`). Trivial laxity: `+14:30` is accepted (`peak.py:132` allows `oh == 14` with any minutes) though not a valid ISO offset.
- **Demotion semantics** (direction 2): with the primary in peak and fallbacks BUSY, the primary is `queue_candidate` (`control.py:1403-1411` step 1), so the request waits on the primary's gate and is served — identical outcome to pre-025 when the primary is BUSY, and a short queue wait (not a failure) when it is merely in-peak. `queue_candidate is None` requires the primary to be CLOSED/UNKNOWN/missing — conditions peak cannot create — so `no_eligible_candidates` cannot be newly reached. DEGRADED backstop is untouched: `not fresh_enough` precedes the demotion branch (`control.py:1076-1077`), and a non-primary DEGRADED in-peak provider stays a backstop; the primary DEGRADED in-peak drops from immediate to queue but keeps the queue-backstop/terminal-fallback roles. Pace interplay verified: in-peak providers never enter the immediate tier, so pace never scores them.
- **Store migration** (direction 3): `ALTER TABLE` failures are caught (`config_store.py:203-210`) and — because DDL is transactional and `commit()` is outside the per-column loop — a mid-migration failure rolls back cleanly, leaving the table untouched for the next boot; column indices in `_load_from_db` match the named `SELECT` list, so ordering is safe. No import cycle: `peak.py` imports only stdlib, and `config_store` imports it lazily. See finding 1 for the load-path JSON gap and finding 2 for the stale-PUT wipe.
- **GUI credential paths** (direction 4): all enumerated paths are safe — the selector wins, the inference fallback only fires when `#pf-key-mode` is absent, which a real browser never produces (a `<select>` with valued options always has a selection); env-with-empty-var 400s with rollback via `_validate_row:693-697` + the PUT build-failure rollback (`admin.py:2609-2633`); stored-mode keep/require semantics are correct (`hasKeptKey` at `dashboard.html:682` matches the server's keep-on-absent at `config_store.py:363-370`); TOML-stored requires re-entry; passthrough is explicit. See findings 3 and 4 for the two UX gaps.
- **Secrets** (direction 5): no new echo path. `_peak_status` carries only specs/epochs (`admin.py:126-143`); the masked surface still excludes `api_key_stored` (`config_store.py:649,660-670`); the GUI shows only `api_key_hint` (last 4, `esc()`'d — quote-safe for the attribute context, `dashboard.html:115-119,289`); logs name rows/fields, never values (`config_store.py:284-288,349`); rollback/tombstone paths carry the raw credential only into `upsert`, never into serialization.
- **Tests** (direction 6): all new tests fail against reverted code (module import errors, missing `in_peak` kwarg, missing demotion assertions, missing columns); no tautologies found — the always-on complementary-window trick genuinely pins the shell wiring without wall-clock flakes.
- **Overclaims** (direction 7): the commit-2a0500b "validated on load" claim (finding 1) and the plan's "warning inline" (finding 4) and "quick form" (finding 3) promises are the substantive ones; the badge wording (finding 6) is cosmetic.
