# Cross-lineage review (plan-026) — opencode-go/deepseek-v4-flash, 2026-08-11

## VERDICT: request-changes

The three commits are, on the whole, unusually disciplined work: Wave 1's behavior-preservation claim held up under direct line-by-line comparison of the old and staged `route_decision`; Wave 2's deliberate changes are each documented and pinned by mirrored tests; Wave 3's "reorders, never resurrects" property is verified at every path I could find (core rank stage, stickiness, queue-candidate selection, reroute alternatives, both snapshot surfaces). But Wave 2.3's "primary computed once" change has one untested interaction with the reroute re-pin logic that creates a genuine, narrow behavioral regression — exactly the class of thing the review was asked to hunt for.

## BLOCKING

### B1. W2.3 leaves a stale pin on a usage-erroring fallback when the reroute lands on the effective primary — repeated failed round trips
`src/switchboard/proxy.py:1506` (`primary = plan.terminal_fallback`) + `proxy.py:1744` (`if rerouted_to is not None and served and rerouted_to != primary:`)

Trace (route `(alpha, beta, gamma)`, model map excludes `alpha`, so the effective primary is `beta`; `gamma` is a model-servable fallback; reroute enabled):

1. `beta` is BUSY → `gamma` is admitted → `acquired(gamma) != primary(beta)` → pin `gamma` (`proxy.py:1599-1608`).
2. `gamma` returns 429 → reroute → `beta` serves. `rerouted_to == beta == primary` → the re-pin at `proxy.py:1744` **does not fire**, and nothing else touches the affinity entry (the loop deliberately never writes a pin mid-loop, `proxy.py:1806-1812`). The `gamma` pin survives.
3. Next request: the plan's stickiness sees the `gamma` pin, `gamma` in IMMEDIATE and fresh, within dwell → dwell-fronts `gamma` again (`control.py:1294-1297`) → `gamma` 429s again → reroute to `beta` again. **The conversation oscillates, paying a failed upstream round trip per request**, until `gamma`'s 429s finally saturate its gate and it drops out of IMMEDIATE.

Pre-026 (verified against `3023160:src/switchboard/proxy.py`), `primary` was `candidates[0]` = `alpha`, so `rerouted_to(beta) != primary(alpha)` was true and the successful reroute **re-pinned `beta`**, retiring the stale `gamma` pin — the behavior the comment at `proxy.py:1745-1747` documents as the intent ("Re-pin so later requests go straight here instead of repaying the exhausted provider's failed round trip"). W2.3 silently inverted that for the effective-primary case, and none of the Wave 2 tests in `test_integration_plan010.py` (which cover the no-reroute cases: `test_model_filtered_primary_is_not_a_failover`, `test_model_filtered_primary_creates_no_affinity_pin`, `test_effective_primary_still_pops_a_pin_naming_someone_else`) exercise reroute × effective primary.

Fix direction: on a successful reroute, if `rerouted_to == primary` and the stored pin names a different provider, pop it (mirroring the failback accounting at `proxy.py:1621-1623`) — or re-pin unconditionally; a pin naming the effective primary is inert for fronting in API-key mode (`control.py:1346-1358` requires `pin_conversations` for the hold) and correct in conversation-pin mode. Add a test: pinned fallback 429s → reroute to effective primary → assert the pin no longer names the failed provider.

## NON-BLOCKING

### N1. `ModelMapManager` migration lacks the failure-handling wrapper its parity claim points at
`src/switchboard/model_map.py:54-61` vs `src/switchboard/config_store.py:196-212`

The docstring says "Same idempotent shape as `ConfigStoreManager._migrate_columns`" — the PRAGMA/ALTER shape is identical, but `config_store` wraps schema+migrate+commit in `try/except sqlite3.Error` and starts empty ("Boot must not crash on a bad store file"), while `ModelMapManager.__init__` runs `CREATE TABLE` / `_migrate_columns` / `commit` / `_load_from_db` unprotected. Practically mitigated: `ModelMapManager` shares `route_table.db` and `RouteTableManager` (`route_table.py:36-66`) constructs first in `cli.py:778` and also doesn't wrap, so a corrupt/read-only store already crashes boot upstream of this point. Still, the claimed parity is shape-only, and this is a new failure surface at a place where the sibling store deliberately degrades. Either wrap it the same way or soften the docstring.

### N2. `affinity_failbacks_total` can count a pop that is no failback after a model-map edit
`src/switchboard/proxy.py:1621-1623`

When a model-map edit changes the effective primary (e.g., the configured primary becomes servable again), a pin naming the previous effective primary is popped and `record_affinity_failback()` fires — but nothing failed back; the route simply re-derived the primary. The W2.3 metrics claim in the commit covers `failovers` ("only a genuine move off a provider that could have served") and is correct; `affinity_failbacks_total` inherits the old semantics and drifts on config edits. Cosmetic metrics noise, worth a note in the commit or a comment at the pop site.

### N3. Wave 3 seam: `preference_rank` is exposed by the API but not rendered by the Routing Explain card
`src/switchboard/admin.py:1557-1565` (per-assessment `preference_rank`) vs `src/switchboard/static/dashboard.html:1579-1584` (only the top-level `preference` stat line)

Consistent with the commit message ("one stat line"), so not a defect — but a per-assessment `preference_rank` field with a `null`/index contract that only the curl consumer can see. If the field is meant to answer "why is zai in front", the card should render it (e.g., a marker on rows whose `preference_rank === 0`); otherwise the API field is dead surface.

### N4. `pace_failover` reason degrades to `failover` when a preference reorders the tier under PACE
`src/switchboard/control.py:1586-1593`

With a preference partitioning the IMMEDIATE tier into singleton groups, `_apply_strategy_order` returns `False` for each group (size < 2), so `pace_changed` is `False` even though the preference moved a fallback to the front; the reason becomes `"failover"` rather than `"pace_failover"`. Cosmetic (the decision log still shows a genuine failover), but it means the "why did this go to zai" signal loses the pace distinction precisely when a preference is in force. Options: treat preference reorder as its own reason (`"preference"`), or leave it and document.

### N5. Runtime-deleted provider leaves a stale model-map alias + preference until the entry is rewritten
`src/switchboard/model_map.py:181-207` (alias/`valid_providers` scrubbing is load-time only)

If a provider is deleted via `DELETE /admin/providers/<name>` at runtime, its model-map aliases (and any preference naming it) survive in memory. This is safe — the provider has no state, so `_stage_classify` skips it and `preference_applies`/`_stage_rank` can't resurrect it (verified) — and the GUI still shows the dead alias in the map table (pre-existing behavior for aliases; the preference inherits it). Non-issue for routing, but the map table now silently shows a preference entry that can never rank.

## Verified-and-cleared (the load-bearing claims)

- **Wave 1 preservation (attack 1):** I compared old `route_decision` (base `3023160`) against Wave 1's staged version branch by branch: the classify truth table (including the DEGRADED-primary and UNKNOWN-availability fall-throughs), queue-candidate preference order (primary-in-queue → first queue member → primary-in-immediate → first backstop), the PACE-only post-dwell inert rule, the no-pin fronting, all four demotion predicates (including the `over_24h`/`in_peak` primary-demotion exceptions), the `_stage_filter` terminal-fallback semantics (`model_unservable` keeps the original primary; `capability_filtered` keeps the servable primary), and every reason string are semantically identical. I found no drift in untested paths.
- **W2.1 headroom flip (attack 1/5):** confirmed it is a Wave 2 deliberate change (old/Wave 1: PACE-only inert; Wave 2: `_ranks_immediate_tier`), pinned by `test_headroom_post_dwell_pin_goes_inert` mirroring the pace tests. `headroom_ranking=True` + `strategy=ordered` also changes behavior (documented intent: "treats the legacy headroom_ranking = true as headroom").
- **`x-route-plan-key` (attack 2):** in `_CONTROL_HEADERS` (`proxy.py:221`), stripped by `_filter_request_headers` on every egress path — the reroute loop re-invokes `_forward`/`_filter_request_headers` per attempt, so both the initial and rerouted forwards strip it. Not leaked in any error message, decision-log entry (`route_key_hash[:16]+"..."`), or the route-plan response.
- **`/admin/route-plan` (attack 2):** admin-auth parity with `/admin/quarantine`; fully read-only (affinity=None, `snapshot_provider_state` reads only, healthy-since copied, no `record_decision`); user-initiated via button click, not polled, so no 5 s-poll DoS; O(candidates) in-memory per call (`next_boundary` is not in this path — it's only in `_provider_status`).
- **Opportunistic retirement (attack 4):** `_opportunistic_target` fully gone from src; the four fields parse from TOML and stored overlays, warn once per boot at the single fold-in seam (`cli.py:1025`), `PUT` 400s with the named retirement message (`admin.py:1838-1840`), reporting surfaces derive from `MUTABLE_ROUTING_FIELDS` so GET no longer advertises them; the only remaining `"opportunistic"` reason reference is a negative assertion in a test. No boot-crash path found for old overlays.
- **Wave 3 preference (attack 5):** no resurrection path exists in the core (rank permutes only `immediate`), the shell (quarantine subtracts from `servable_providers` before the decision; reroute alternatives come from the plan), or either snapshot surface. An ACTIVE pin outranks preference (dwell branch precedes `_ranks_immediate_tier`, `control.py:1294`); an expired pin goes inert under preference-applies — documented and tested (`test_preference_makes_an_expired_pin_inert_under_ordered`). The flap-margin group scoping matches the doc: within-group deadband, cross-group silence, with the exact "near-tie that used to trip the whole-tier deadband now fronted by preference" case pinned by `test_preference_dominates_the_flap_margin_across_groups`. Malformed/duplicate/alias-less preference JSON on load → warning + unset, never a crash (`_coerce_preference`).
- **Migration (attack 6):** malformed preference JSON on load handled; see N1 for the ALTER-failure parity gap.
- **Wave-3 fields in Wave-1 surfaces (attack 7):** `status.json` keeps `model_map` shape and adds `model_preferences`; `GET /admin/model-map` always emits `preference`; the route-plan endpoint emits `preference` + `preference_rank`; see N3 for the one unrendered field.

No commit message or plan-doc claim I checked overstates the code except the "same migration as config_store" parity framing in N1 and the unmentioned reroute regression in B1.
