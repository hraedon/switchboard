## On the project

switchboard's architecture keeps impressing me. The pure routing core
(`control.py`) absorbed four new dimensions this session — per-provider
soft_threshold, a per-provider healthy-since dict, conversation pinning with
a new reason code — and each was a localized addition to a single function
(`route_decision`) with no structural change. That's the dividend of the
"decision is the asset, keep it pure" discipline: the routing logic is a
flat, ordered pipeline over plain data, and every new signal slots in as one
more conditional in that pipeline. The streaming path (`_forward`) is the
other load-bearing invariant, and it held: speed instrumentation and
conversation fingerprinting both added observation without touching the
chunk-forwarding loop or altering body bytes.

The GUI is the weakest part of the codebase — vanilla JS with innerHTML
string-building, no framework, tested only by node shims that stub a handful
of DOM APIs. It works and the harnesses pin the load-bearing behaviours, but
it's fragile. Three managed sections (default-route, add-provider,
route/model management) now share the "lives outside #app + freeze-on-edit"
pattern, which is the right call given the 5s poll rebuilds #app wholesale.
But any future GUI work that needs richer DOM interaction will outgrow the
shim and need a real headless browser.

## On the work done

**What went well:** the subagent fan-out was the highest-leverage move. Three
parallel reviewers (core/shell/plans) cross-corroborated — both the core and
shell reviewers independently flagged `soft_threshold` as dead config, and the
plans reviewer mapped every "proposed" plan against the actual code, catching
that Plans 017/020 said "proposed" for work that had shipped. The deepseek
adversarial reviews on my own changes caught real bugs I'd have shipped: the
tokens_per_sec filter mismatch, the RecursionError DoS in the fingerprint
extractor, and the opportunistic-quota-burn-diverts-a-pinned-conversation bug.
Those reviews earned their cost.

**What I'm confident in:** the pure-core changes (soft_threshold wiring,
healthy_since dict, conversation pinning suppression) are well-tested and the
adversarial reviews confirmed the control flow. The token_budget wall_ts fix
is correct across reboots (wall-age filtering + monotonic-frame translation).
The HistoryStore collision fix is clean.

**What I'd want a second pair of eyes on:** the GUI forms are tested by shims,
not a browser — the providers_form and routes_models harnesses stub
`confirm`/`alert`/`fetch` and a minimal DOM, so they prove the logic but not
real rendering. The speed-statistics instrumentation in `_forward` is timing
that I verified doesn't touch the streaming loop, but TTFB/duration semantics
(request-open → response-headers vs request-open → first-client-byte) are a
judgment call I made without a spec. The conversation-pinning "pin on first
request to the primary" path is subtle — it pins even when the primary serves
happily, which is the point, but it means the affinity table grows with every
new conversation (bounded by `affinity_max_entries`, default 1024, with an
eviction counter). The default 1024 is fine for API-key-hash mode but will
evict aggressively in conversation-pinning mode; operators need to raise it.

## Gaps to flag

- **`max_request_body_bytes` is unbounded by default.** The conversation-pinning
  startup guard requires it finite ONLY when `pin_conversations` is on. The
  model_map path buffers bodies without any finite limit today (pre-existing,
  not introduced this session). A model_map deployment with no
  `max_request_body_bytes` has the same memory-exhaustion surface the plan
  flagged for pinning. `cli.py:1022` (buffering condition) + `proxy.py:1625`.
- **Speed stats tokens_per_sec is only available for budgeted providers.**
  The completion-token count rides the existing opt-in `UsageObserver`, which
  is only active when a `[token_budget]` is configured. So a provider with no
  budget gets TTFB/duration but `tokens_per_sec: null`. Coupling speed-token
  data to the budget opt-in is a reasonable first cut but an operator might
  expect tokens/sec for all providers. `proxy.py:1955-1971`.
- **Conversation pinning default `affinity_max_entries=1024` will evict
  aggressively.** The plan recommends 8192 for pinning mode. Operators must
  raise it manually; there's no startup hint when pinning is on and the
  default is left at 1024. `control.py:215`.
- **The GUI has no integration test against a real ASGI server.** The shim
  harnesses prove JS logic but the dashboard is only exercised by node, never
  by the actual uvicorn + httpx path. A regression in the static-serving or
  CSRF cookie flow would pass the shims and fail in production.
  `tests/gui/*.mjs`.
- **`p50` is computed by `SpeedSampler.summary` but never surfaced** — neither
  Prometheus nor the dashboard emits it. Dead data in the status.json payload.
  `speed.py:72`.
- **Plan 019 Phase 3 status update may surprise.** I re-scoped the plan's
  status to "Phase 1+2 done via 018/020, Phase 3 implemented," but the plan
  body still describes Phase 1/2 in detail (sluice vendoring, credential
  injection) as live work. A reader of the plan body alone would think those
  phases are pending. `plans/019-...:7`.
- **The `route_decision` docstring's numbered steps still list 10 steps where
  the routing-model.md §3 lists 11** (the model-filter step was added to the
  code and the routing-model doc but the function docstring's ordering
  comment wasn't fully reconciled — I added model-filter to the guarantees
  list but the step-numbering in the docstring vs the doc is a residual
  mismatch). `control.py:417`.
