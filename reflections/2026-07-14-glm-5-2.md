## On the project

switchboard's architecture continues to mature well. The pure routing core (`control.py`) remains the project's strongest asset — every new feature (headroom filtering, model servability, affinity) is added as pure data + pure functions, with the proxy as a thin shell. The import boundary test enforces that `control.py` imports nothing outside stdlib.

The project now has a complete Plan 010 + Plan 011 implementation: overload breaker (reactive), low-interactivity surfacing (proactive via sluice), model-aware failover with rewrite, threshold estimator (pure core + shell), and usage-aware headroom filtering. The routing decision is a layered system: gate state → overload breaker → low-interactivity → headroom → model servability → capability filtering → affinity. Each layer is independently testable and opt-in.

The CI workflow is now in place — 3.12/3.13/3.14 with ruff + mypy + pytest, plus the identifier gate. This satisfies AGENTS.md hard rule 7 ("Validate on CI early; distrust green local gates"). The CI installs sluice from GitHub (since sluice isn't on PyPI), which required pushing sluice's Feature 0 commit to GitHub first.

## On the work done

**What went well:** The sequential dispatch (Plan 011 first, then Plan 010 WI-10) avoided edit conflicts on shared files. The adversarial review process caught significant issues: the Plan 010 reviewer found 2 CRITICAL issues (persistence failures crashing live requests, load() crashing on corrupted state), 2 HIGH issues (sync I/O blocking, non-defensive deserialization), and 8 MEDIUM issues — all fixed. The Plan 011 reviewer found missing unit tests for headroom filtering and the admin config omission — all fixed.

**What was awkward:** The CI initially failed because sluice wasn't published to PyPI and the workflow tried to resolve it from there. Fixed by installing sluice from GitHub in the same `uv pip install` command. Then CI failed again because sluice's Feature 0 commit (with `is_low_interactivity()` and `tokens_in`/`tokens_out` fields) hadn't been pushed to GitHub. Had to push sluice first, then re-run switchboard CI. This cross-repo dependency is inherent to the family architecture but worth noting for future sessions.

**What I'm confident in:** The pure routing core is correct — headroom filtering, model servability, and affinity are well-tested with unit tests that assert directly on `AdmissionPlan` fields. The estimator shell is hardened: persistence failures don't crash requests, load() survives corrupted state, deserialization is defensive, and state is provider-scoped. The integration tests verify end-to-end behavior with mock upstreams.

**What I'd want a second pair of eyes on:** The estimator's `maybe_sample` is called on every proxied request, which means SQLite writes happen on the hot path. The fix skips writes when state hasn't changed, but the first sample in a new window will always write. For high-traffic deployments, a background flush or async write would be better. Also, the `_dict_to_state` deserialization uses `.get()` with defaults but doesn't validate types — a corrupted store could produce an `EstimatorState` with wrong types that silently produce incorrect estimates.

## Gaps to flag

- **Estimator SQLite writes on hot path**: `maybe_sample` is called per-request and writes synchronously to SQLite. The "skip if unchanged" guard helps, but the first sample in a new window always writes. `estimator.py:95-103`
- **`_dict_to_state` doesn't validate types**: Uses `.get()` with defaults but doesn't coerce/validate types. A corrupted store could produce an `EstimatorState` with string values where ints are expected. `estimator.py:120-165`
- **`cli.py` accesses `route_table.db` (was `_db`)**: Now uses the public `db` property, but the coupling between estimator and route table SQLite is still tight. A separate DB or a shared connection manager would be cleaner. `cli.py:470`
- **sluice version mismatch**: `sluice.__version__` says "1.3.1" but the GitHub main branch has Feature 0 (unreleased). switchboard's `pyproject.toml` pins `sluice>=1.3.1,<2.0` which works but is misleading. `sluice/src/sluice/__init__.py`, `switchboard/pyproject.toml:13`
- **CI installs sluice from GitHub main**: This means CI breaks if sluice's main branch is ahead of switchboard's expectations. A pinned commit or tag would be safer. `.github/workflows/ci.yml:37`
- **No pip-audit in CI**: sluice's CI has pip-audit; switchboard's doesn't. Could add it for security. `.github/workflows/ci.yml`
- **`headroom_threshold` not in `/admin/config` test assertions**: The admin config response now includes `headroom_threshold`, but the existing tests don't assert on it. `tests/test_admin.py`
