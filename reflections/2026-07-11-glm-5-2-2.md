## On the project

switchboard's architecture is maturing well. The pure routing core (control.py) remains the project's strongest asset — every new Plan 008 feature (capabilities, affinity, dwell) was added as pure data + pure functions, with the proxy as a thin shell. The import boundary test now enforces both directions: control imports stdlib only, and no module imports underscore-prefixed sluice symbols.

The project's biggest remaining risk is the gap between the Plan 008 type definitions and their full integration. ProviderCapabilities and RouteEntry.required_capabilities exist in the pure core and are tested, but `snapshot_provider_state` never populates `capabilities` (always None), and the admin API / TOML config don't accept `required_capabilities`. The capability filtering is technically dead code in production — it only activates when tests manually construct ProviderState with capabilities. This is acceptable for now (the types are ready, wiring is the next step), but it should be clearly documented as "types defined, integration pending."

The sluice dependency is now properly bounded (`<2.0`), and the clean wheel install test verifies the package works without sibling source directories. The streaming integration tests (6 tests in test_streaming.py) cover the Plan 006 §6 requirements — disconnect during all streaming phases, body size limits, and upstream idle timeout.

## On the work done

**What went well:** The three-way parallel dispatch (sluice promotion, reflection gaps, Plan 008 control types) was efficient — each subagent worked independently and the results merged cleanly. The adversarial review process was the most valuable step: two independent reviewers found 15+ issues, 4 of which were critical. The second review round caught a subtle dead-code regression introduced by the first round's fixes.

**What was awkward:** The `_admit` method went through three iterations. The original had a freshness-policy bypass in the second pass. The first fix (restrict to `plan.immediate_candidates`) introduced dead code because the `tried` set made the second pass a no-op. The final version removes `tried` entirely and lets the second pass retry with additional health checks. This iterative debugging could have been avoided with more careful analysis upfront.

**What I'm confident in:** The pure routing core (control.py) is correct — the capability filtering, affinity stickiness, and dwell/failback logic are well-tested with 14+ new tests covering edge cases. The import boundary is clean and enforced. The streaming tests verify permit release on disconnect in all phases.

**What I'd want a second pair of eyes on:** The affinity eviction uses FIFO (oldest insertion-order key), which is simple but may not be optimal — an LRU that touches the accessed key would keep active routes sticky longer. The `more_body: False` fix after upstream error is in the right place, but I'd want to verify it doesn't interact badly with ASGI servers that have already started sending.

## On what remains

**Needed before shipping:**
1. Wire `ProviderCapabilities` through `snapshot_provider_state` — populate from provider config metadata so the capability filtering actually runs in production.
2. Wire `required_capabilities` through the admin API (`handle_route_add`) and TOML config (`load_from_config`) so routes can declare capability requirements.
3. Disconnect detection during queue wait — `_admit` does not monitor `receive()` for `http.disconnect` while waiting on `queue_candidate`. A client that disconnects during the queue wait will still acquire a permit and forward to upstream for a gone client. This is a known gap from the prior session's reflection, still unfixed.
4. Plan 008 WI-6 (singleton production lifecycle) — reuse sluice's singleton/fencing, add leadership-aware readiness, safe drain.
5. Plan 008 WI-1 (versioned config schema) — schema validation, migrations, merge precedence, `switchboard config validate`.

**Nice to have:**
6. Plan 008 WI-7 (credential broker) and WI-8 (admin-plane isolation) — these are larger features that should wait for the capability wiring.
7. `ReplayBoundary` enum is defined but not consumed by the proxy — it needs to be wired into the streaming lifecycle to actually enforce the replay boundary table.
8. The `_admit` second pass now retries all `immediate_candidates` — this is correct but means a provider that lost the snapshot race gets retried twice in quick succession. A small delay or backoff between passes might reduce thundering herd.
9. The affinity `healthy_observations` field is defined but never incremented — the proxy doesn't track healthy observations for failback decisions.

## Gaps to flag

- **Capability filtering is dead code in production**: `snapshot_provider_state` never populates `capabilities` (always None), so `_satisfies_capabilities` always returns True. The filtering only works in tests. `providers.py:239-246`
- **No disconnect detection during queue wait**: `_admit` waits on `gate.acquire(timeout=remaining)` without monitoring `receive()`. A client disconnect during queue wait is not detected until `_forward` starts. `proxy.py:641-655`
- **`ReplayBoundary` is unused**: The enum is defined but the proxy never returns or checks it. The replay boundary table from Plan 008 §6 is not enforced. `control.py:49-62`
- **`healthy_observations` is dead**: `RouteAffinity.healthy_observations` is set to 0 by the proxy and never incremented. The pure core never reads it. `control.py:95`, `proxy.py:570`
- **Affinity eviction is FIFO, not LRU**: `next(iter(self._affinity))` evicts the oldest insertion-order key, not the least recently accessed. An active long-lived route could be evicted in favor of a newer but inactive one. `proxy.py:575-577`
- **`_cancel_task` suppresses all exceptions silently**: `contextlib.suppress(asyncio.CancelledError, Exception)` hides upstream errors without logging. `proxy.py:100-102`
- **sluice version mismatch**: `sluice.__version__` says "1.3.0" but `pyproject.toml` says "1.3.1". Pre-existing, not caused by this session. `sluice/src/sluice/__init__.py`
