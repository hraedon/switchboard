## On the project

switchboard is a routing layer above multiple sluice-style gates. The design is sound: pure routing core in control.py (stdlib only, no I/O, no clock), thin async shell in proxy.py, provider contexts that compose sluice building blocks. The AGENTS.md conventions are clear and well-enforced by the import boundary test.

The project's biggest risk is its dependency on sluice's private APIs. The proxy imports underscore-prefixed symbols from `sluice.admin` (`_cors_extra_headers`, `_build_set_cookie`, `_read_body`, `check_csrf`). Plan 007 addresses this, but until then, a sluice refactoring could break switchboard silently. The `pyproject.toml` pins `sluice>=1.3.1` with no upper bound, which is not a deliberate pin as WI-006.5 requires.

The plans (006-009) are exceptionally well-written. They name specific work items, acceptance criteria, and non-negotiable outcomes. Plan 009 (the north-star charter) explicitly says it's not an execution plan, which prevents scope creep.

## On the work done

**What went well:** The pure core revision (control.py) was straightforward — the categorical model (Availability + SignalFreshness) is cleaner than the scalar pressure comparison. The property/invariant tests from Plan 006 §6 mapped directly to test functions. The adversarial review process caught real bugs I would have missed.

**What was awkward:** The Plan 001-005 implementations were never committed, so I had to commit them alongside Plan 006 in one giant commit. A staged history would have been better. The `_admit` method's second pass (trying remaining eligible candidates) was the hardest to get right — the adversarial reviewers correctly identified that it was trying UNKNOWN providers, violating the fresh-only-for-failover policy.

**What I'm confident in:** The pure routing core (control.py) is correct — the property tests cover all invariant combinations. The bounded metrics (deque + eviction counter) are correct. The config validation catches the important failure modes.

**What I'd want a second pair of eyes on:** The `_admit` exception handling — I wrapped the `_admit` call in a try/except that returns 503, but if `_admit` acquires a permit and then raises (e.g., CancelledError during queue wait), the permit may leak. sluice's `PermitGate.acquire` may or may not grant the permit before a CancelledError — this needs investigation. Also, the `DashboardTruthSource.fetch` method uses `time.time()` (wall clock) for staleness comparison while receiving `now_monotonic` — this is a pre-existing issue I didn't fix.

**Nice to have:**

6. The `DashboardTruthSource` uses `time.time()` for staleness instead of `now_monotonic` — should be fixed for testability.

## Gaps to flag

- **`_admit` permit leak on CancelledError**: If `gate.acquire(timeout=remaining)` raises after internally granting a permit, the permit leaks. The try/except in `_proxy_request` catches it and returns 503, but doesn't release the leaked permit. `proxy.py:516-522`
- **`DashboardTruthSource` wall-clock staleness**: Uses `time.time()` inside `fetch()` while receiving `now_monotonic`. Makes tests time-dependent and violates the "pass time in" convention. `dashboard.py:157`
- **Missing disconnect/streaming tests**: Plan 006 §6 explicitly requires tests for downstream disconnect during every streaming phase. None exist. This is a significant test coverage gap for a streaming proxy.
- **`sluice.admin` private imports**: `switchboard.admin` and `switchboard.proxy` import `_build_set_cookie`, `_cors_extra_headers`, `_read_body`, `check_csrf` from `sluice.admin`. These are underscore-prefixed and could change without notice. `admin.py:22-30`, `proxy.py:43-50`
- **No upper bound on sluice dependency**: `pyproject.toml` has `sluice>=1.3.1` with no upper bound. A breaking sluice 2.0 could silently break switchboard. `pyproject.toml:13`
- **`_validate_config_pre_build` doesn't validate provider type**: It validates upstream/target format but doesn't call `get_provider()` to verify the type exists. An unknown type fails later in `build_provider_context` with a less helpful error. `cli.py:82-112`
- **Prometheus metrics lack `evicted_decisions`**: The bounded metrics have an `evicted_decisions` counter, but it's not exposed in `/metrics`. Only in `/status.json`. `admin.py:161-232`
- **`preference_rank` field is dead**: `ProviderState.preference_rank` is set but never read by `route_decision`. The ordering comes from the candidate list iteration order. `control.py:58`, `control.py:163-199`
